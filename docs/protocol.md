# Car Interface serial protocol v1

This document is the normative host/ESP32 wire contract for protocol version 1.
The older prototype commands (`V 50`, `W 1795`, `S 1`, `Q 1`, and variants) are
not protocol v1 and must not be accepted by protocol-v1 firmware. The host can
select the separate, write-only `school_car_legacy_v0` compatibility profile
described below; it is never auto-detected.

> [!IMPORTANT]
> The repository does not yet establish that a particular physical firmware
> build implements this contract. Hardware mode is release-blocked until the
> firmware artifact is identified and the conformance tests pass.

Normative terms **MUST**, **MUST NOT**, **SHOULD**, and **MAY** indicate protocol
requirements.

## Transport

- 8-bit ASCII, newline-delimited (`LF`, byte `0x0A`).
- One command and one corresponding response per sequence number.
- Default baud is 115200; both endpoints MUST use the configured value.
- A complete frame, including `!`, `*`, four checksum digits, and `LF`, MUST NOT
  exceed 128 bytes.
- Embedded CR/LF, non-ASCII bytes, empty fields, lowercase checksum digits, and
  extra delimiters MUST be rejected without changing actuator output.
- Receivers MUST bound buffers and discard/resynchronize safely after an
  overlength or malformed line.

## Frame grammar

```text
command = "!CAR,1,CMD," sequence "," opcode [ "," value ] "*" crc16 LF
ack     = "!CAR,1,ACK," sequence "*" crc16 LF
nack    = "!CAR,1,NACK," sequence "," fault-code "*" crc16 LF
```

- `sequence` is a canonical decimal integer from 0 through 2147483647: no sign
  and no leading zero except the value `0`.
- `opcode` and `fault-code` are uppercase ASCII protocol tokens. A fault code
  begins with `A-Z` and contains at most 32 characters from `A-Z`, `0-9`, and
  underscore.
- `crc16` is exactly four uppercase hexadecimal digits.

The checksum covers the bytes between, but excluding, `!` and `*`. It uses
CRC-16/CCITT-FALSE: polynomial `0x1021`, initial value `0xFFFF`, no reflection,
and no final XOR.

For example, the checksum input `CAR,1,CMD,0,SPD,25` produces `E24B`:

```text
!CAR,1,CMD,0,SPD,25*E24B\n
```

## Commands

| Opcode | Value | Meaning | Priority |
| --- | --- | --- | --- |
| `SPD` | canonical integer `-100..100` | normalized signed propulsion request; `0` is a safety command | control/safety |
| `STR` | canonical integer `-100..100` | normalized signed steering, negative left and positive right after qualification | control |
| `BRK` | `0` or `1` | release/assert actuator brake; `1` zeros propulsion; `0` does not arm the host state and is sent only after the explicit re-arm interlock | control/safety |
| `MOD` | `MANUAL` or `AUTONOMOUS` | choose request source; mode change does not arm; `AUTONOMOUS` is reserved and has no v0.1 operator path | control |
| `ARM` | `0` or `1` | inhibit/permit bounded motion; `0` zeros propulsion and asserts brake | control/safety |
| `HBT` | none | heartbeat proving a valid host session | background |
| `EST` | none | latch E-stop, zero propulsion, assert brake | emergency |
| `RST` | none | request latch reset; firmware MUST check safe preconditions | safety |

Examples generated by the protocol-v1 codec:

```text
!CAR,1,CMD,1,STR,-10*27F4
!CAR,1,CMD,2,BRK,1*2385
!CAR,1,CMD,3,MOD,MANUAL*3DDB
!CAR,1,CMD,4,ARM,1*DED2
!CAR,1,CMD,5,HBT*F2CC
!CAR,1,CMD,6,EST*6E0D
!CAR,1,CMD,7,RST*02AF
```

Values are normalized requests, not physical units. Firmware MUST clamp or map
them only within the qualified actuator limits. It MUST NOT interpret an invalid
or out-of-range value by truncation, wrapping, or retaining an earlier command.

## Responses

A syntactically valid command MUST receive exactly one response with the same
sequence:

```text
!CAR,1,ACK,7*2CFD
!CAR,1,NACK,8,BAD_CRC*E3A7
```

`ACK` means the command was validated and applied to the firmware state. It does
not prove mechanical motion or braking. `NACK` means the command was not applied
and includes a stable uppercase fault code.

Recommended NACK codes include:

| Code | Meaning |
| --- | --- |
| `BAD_CRC` | Checksum mismatch |
| `BAD_FRAME` | Delimiter, field count, encoding, or canonical-value error |
| `BAD_VERSION` | Protocol name/version unsupported |
| `BAD_SEQUENCE` | Invalid or unacceptable sequence |
| `BAD_OPCODE` | Unknown command opcode |
| `OUT_OF_RANGE` | Valid value form outside allowed range |
| `NOT_ARMED` | Motion requested while inhibited |
| `ESTOP_LATCHED` | Command conflicts with latched E-stop |
| `WATCHDOG_TIMEOUT` | Watchdog latch requires a safe reset or reconnect |
| `UNSAFE_RESET` | Reset prerequisites are not satisfied |
| `INTERNAL_FAULT` | Firmware cannot safely apply the command |

For a frame whose sequence cannot be recovered reliably, firmware SHOULD emit a
diagnostic response only if doing so cannot be confused with an ACK. It MUST
always retain or enter safe output.

## Sequence semantics

- The host allocates a new sequence for every transmitted command, including
  heartbeat.
- It MUST accept only an ACK/NACK matching the outstanding sequence.
- A mismatched, duplicate, unsolicited, or late response is a protocol error and
  MUST NOT authorize motion.
- Retries, if implemented, use the same sequence and identical command; firmware
  MUST make duplicates idempotent and repeat the original response.
- A new host session starts with safe outputs and a fresh sequence context.
- Before sequence exhaustion, the host MUST safely disarm and reconnect rather
  than silently wrap into an ambiguous active session.

## Timing and watchdog

The code-level protocol contract defaults to:

| Setting | Protocol default |
| --- | --- |
| ACK timeout | 0.2 seconds |
| Heartbeat interval | 0.1 seconds |
| Firmware watchdog timeout | 0.5 seconds |

Application configuration may select qualified values, but the firmware
watchdog timeout MUST exceed heartbeat interval plus ACK timeout, and the
qualification must retain adequate scheduling margin.

Every v1 command requires acknowledgement. On missing ACK, NACK, malformed
response, sequence mismatch, transport failure, or repeated protocol error, the
host safety layer transitions to fault and evicts pending motion.

Firmware MUST independently set speed to zero, assert brake, and inhibit motion
when it does not receive valid in-session traffic before its watchdog expires.
Invalid frames MUST NOT refresh the watchdog. A host reconnect, firmware reset,
or watchdog event MUST NOT restore the previous motion command.

## Startup and reset

1. Firmware boots with zero propulsion, brake asserted, and motion inhibited.
2. Host opens the transport and validates protocol v1 using only non-motion
   traffic/safety commands.
3. Host asserts disarm and brake and requires matching ACKs.
4. Application completes required-device and freshness checks.
5. Explicit operator arm permits later bounded motion.

Releasing an operator brake input does not satisfy step 5. The host remains in
`BRAKING` until it receives a fresh neutral controller input and the operator
explicitly arms. Only a later validated drive operation may send `BRK,0`; no
queued motion is replayed.

`RST` only requests clearing a latch. Firmware MUST reject it while its local
fault persists. A successful reset remains zero-speed and braked; host and
firmware require a new explicit arm.

## Conformance tests

Firmware qualification MUST test golden frames plus wrong CRC, lowercase CRC,
non-ASCII input, embedded newline, empty/extra fields, overlength input, unknown
version/opcode, all range boundaries, noncanonical integers, response sequence,
duplicate command behavior, partial input, disconnect, host crash, watchdog,
reset, and boot during a non-zero prior command.

See [Firmware compatibility](firmware-compatibility.md) and
[Hardware qualification](hardware-qualification.md).

## Explicit school-car legacy compatibility

`school_car_legacy_v0` is a host compatibility profile, not protocol v1. It is
selected only through configuration and never by inspecting serial traffic.
The default remains `car_v1`.

The profile writes newline-terminated ASCII commands with no sequence, CRC, or
command-correlated response contract: `A`, `M`, `D F`, `D R`, `V <0..100>`,
`W <calibrated-raw>`, `S 1`, and `Q 1`. Signed speed is dispatched as one
contiguous operation: direction first, then a non-negative speed magnitude.
Steering maps `-100..100` piecewise through configured minimum, center, and
maximum values. Consecutive lines are paced by a configurable interval that
defaults to 50 ms.

Because the demonstrated firmware does not return command-correlated replies,
a successful receipt for this profile means all lines were written to the
serial transport. It is explicitly not marked acknowledged. See
[ADR-0005](adr/0005-explicit-school-car-legacy-profile.md).
